1.4. Lokal CA va TLS server sertifikatini yaratish
SRV-1 da faqat ushbu laboratoriya uchun lokal sertifikatlash markazi va server kalitini yarating. CA private key serverda
qoladi; CLIENT-1 ga faqat ca.crt beriladi.
sudo install -d -m 700 /etc/a2-tls
cd /etc/a2-tls
sudo openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out ca.key
sudo openssl req -x509 -new -sha256 -days 365 -key ca.key -out ca.crt
-subj "/C=UZ/O=A2
Lab/CN=A2 Lab CA"
sudo openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out srv1.key
sudo openssl req -new -key srv1.key -out srv1.csr
-subj "/C=UZ/O=A2 Lab/CN=srv1.a2.lab"

SAN va foydalanish cheklovlarini ko‘rsatuvchi /etc/a2-tls/srv1.ext faylini yarating:
sudo nano /etc/a2-tls/srv1.ext

Fayl mazmuni:
basicConstraints=CA:FALSE
keyUsage=digitalSignature,keyEncipherment
extendedKeyUsage=serverAuth
subjectAltName=DNS:srv1.a2.lab,IP:192.168.57.20

CSR ni imzolang, private key ruxsatlarini cheklang va sertifikat maydonlarini tekshiring:
cd /etc/a2-tls
sudo openssl x509 -req -in srv1.csr -CA ca.crt -CAkey ca.key
-CAcreateserial -out srv1.crt days 120 -sha256 -extfile srv1.ext
sudo chmod 600 ca.key srv1.key
sudo chmod 644 ca.crt srv1.crt
sudo install -o student -g student -m 644 ca.crt /home/student/a2-ca.crt
sudo openssl verify -CAfile ca.crt srv1.crt
sudo openssl x509 -in srv1.crt -noout -subject -issuer -dates -ext subjectAltName

server {

echo '192.168.57.20 srv1.a2.lab' | sudo tee -a /etc/hosts

</dev/null 2>/dev/null | grep -E 'Protocol|Cipher|Verify return code'
curl --resolve wrong.a2.lab:443:192.168.57.20

1.9. Yakuniy integratsion tekshiruv va xavfsiz yakunlash
IPsec qayta tiklangandan keyin SSH va HTTPS ni yana sinang. Bu yuqori qatlam xizmatlari IPsec siyosati mavjud
paytda ham ishlashini ko‘rsatadi:
ssh -i ~/.ssh/a2_ed25519 student@192.168.57.20 'echo SSH_OVER_IPSEC_OK'
curl --cacert ~/a2-ca.crt https://srv1.a2.lab/
sudo ipsec statusall
sudo ip xfrm policy

Ish tugagach VMlarni o‘chirib, o‘qituvchi ko‘rsatmasiga ko‘ra A2-base snapshotiga qayting. Private key yoki
laboratoriya PSK sini umumiy papka, messenjer yoki hisobotga nusxalamang. Agar snapshot ishlatilmasa, o‘qituvchi
keyingi mashg‘ulot uchun konfiguratsiyani saqlash yoki tiklash bo‘yicha alohida ko‘rsatma beradi.

4. Topshiriladigan dalillar
• Ikkala VMning nomi, A2-LAB interfeysi va IP manzili ko‘rinadigan dalillar.
• SSH public key fingerprinti, sshd -t/sshd -T natijasi, muvaffaqiyatli kalitli kirish va rad etilgan password-only urinish.
• TLS sertifikatining subject, issuer, dates va SAN chiqishi; private key mazmuni ko‘rsatilmaydi.

• ipsec statusall hamda ip xfrm state/policy natijalari; kalit materiali va PSK ko‘rsatilmaydi.
• A2-LAB interfeysida ESP/IKE trafikini ko‘rsatuvchi tcpdump dalili.

• Barcha jadvallar, 6–8 gaplik tahliliy xulosa va o‘qituvchi savollariga og‘zaki javob.

7. O‘qituvchi uchun qisqa himoya savollari
• SSH, TLS va IPsec OSI/TCP-IP modelining qaysi qamrovlarida himoya beradi?
• SSH host kaliti bilan foydalanuvchi kalitining vazifasi nimasi bilan farq qiladi?
• PasswordAuthentication no dan oldin nima uchun ikkinchi SSH sessiyasini sinash kerak?
• TLS sertifikatidagi Subject, Issuer va SAN maydonlari qanday vazifa bajaradi?
• curl --cacert muvaffaqiyati nimani isbotlaydi, --insecure esa nega yaroqsiz dalil?
• wrong.a2.lab sinovi nima uchun rad etildi, garchi IP manzil va CA to‘g‘ri bo‘lsa ham?
• IKE SA bilan CHILD SA o‘rtasidagi farq nima?
• Transport rejimida qaysi ma’lumot ochiq qoladi va qaysi qism ESP bilan himoyalanadi?
• ip xfrm state va ip xfrm policy chiqishlari bir-biridan nimani ko‘rsatadi?
• tcpdump da ESP ko‘rinishi foydali yuk shifrlanganini qanday asoslaydi va nimani isbotlamaydi?
• Noto‘g‘ri PSK da ulanish nega o‘rnatilmadi va tiklash muvaffaqiyatini qanday tekshirdingiz?
• Real muhitda IKEv2 PSK o‘rniga sertifikatli autentifikatsiyani qachon tanlaysiz?
